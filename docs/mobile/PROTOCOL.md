# Phone gateway protocol

Wire contract between the coordinator and the iOS app. Schemas live in `src/shared/mobile.ts` and are the source of truth; this file explains them. Swift `Codable` types mirror those schemas field for field.

Protocol version: **1** (`PROTOCOL_VERSION`).

## Transport

* `wss://<magicdns-name>:<port>/ws`, default port 7443.
* The coordinator listens only on its Tailscale addresses (one listener per address from `tailscale ip`), never `0.0.0.0`.
* TLS cert and key come from `tailscale cert <magicdns-name>`, so the phone validates a normal public chain. No ATS exceptions.
* One JSON message per WebSocket text frame. No binary frames.
* `URLSessionWebSocketTask` caps incoming messages at 1 MiB by default; snapshots and history pages can be larger, so the app sets `maximumMessageSize` to 32 MiB.
* Inbound frame limit 16 MiB (uploads). Larger frames close with 4413.
* Server sends a WebSocket ping every 20 s; client also pings on foreground. No app level ping.
* Backpressure: if a connection's buffered output exceeds 4 MiB, or stops draining for 60 s, the server closes with 4408. The client reconnects and resumes.

## Pairing and auth

QR code shown in desktop Settings encodes:

```
daycare://pair?v=1&host=mac.tail1234.ts.net&port=7443&token=<token>
```

* `token`: 32 random bytes, base64url, generated by the coordinator on first gateway start, stored in `gateway.json`.
* The phone stores host, port and token in the Keychain.
* Token is sent in `hello`, never in the URL. Compared in constant time. Wrong token: `error {code: "unauthorized"}` then close 4401. After 5 failures in a minute the server waits 5 s before answering each hello.
* "New pairing code" in Settings rotates the token and closes every phone connection. That is the only revocation.

## Handshake

Client sends first, within 10 s of connecting (else close 4400):

```json
{ "type": "hello", "protocol": 1, "app": "1.0 (12)", "token": "…", "device": "<uuid>",
  "resume": { "epoch": "…", "seq": 4182 },
  "watch": { "sessions": ["<id>"], "deltas": true } }
```

* `device`: UUID minted once per install, kept in the Keychain. A second connection with the same `device` closes the older one with 4409.
* `resume` and `watch` are optional.

Server answers one of:

1. `protocol_mismatch {server, client}` then close 4426. The app shows "Update the Daycare phone app" (or "update Daycare on the Mac" when `client > server`) and stops retrying until relaunch.
2. `welcome {protocol, coordinator, epoch, resumed}` followed by:
   * `resumed: true`: every buffered `event` with `seq` greater than `resume.seq` that passes the watch filter, then live events.
   * `resumed: false`: one `snapshot`, then live events.

Commands are accepted only after `welcome`. A second `hello` is answered with `error {code: "bad_request"}`.

## Snapshot (slim)

```
snapshot { epoch, seq, sessions: MobileSession[], approvals: Approval[], power: PowerState,
           catalog: Catalog | null, unavailable: string[] }
```

* No transcripts. `MobileSession` is `LiveSession` plus `lastEntry`, `lastEventAt`, `preview` (first 200 chars of the newest assistant text).
* `approvals` carries every pending approval with its `choices` and permission event, so the approvals screen works without any transcript.
* `catalog` is null until a desktop has connected to this coordinator at least once (see Catalog).
* `seq` is the hub sequence the snapshot reflects; the next event has a larger `seq`.

## Catalog

`Catalog { locations, accounts, activeAccount, defaultLocation, provider, model, effort, permissionMode, models, efforts }` holds what the new session screen needs. The desktop pushes it over the socket (with config dirs, icon pack and naming settings the phone never sees) on connect and on every settings change; the coordinator persists it, so the phone works with the window closed. Changes reach phones as `catalog` events.

## Events

```
event { seq, event: MobileEvent }
```

`seq` is the hub's global sequence. It increases strictly but **has gaps**, because the gateway filters per connection. Clients store the last `seq` they processed and never assume contiguity.

| kind | fields | sent to |
|---|---|---|
| `session` | `session: MobileSession` | all |
| `removed` | `session, parentId` | all |
| `approval` | `approval` | all |
| `approval-resolved` | `session, request, allowed, cancelled` | all |
| `chat` | `session, entry, event: ChatEvent` | watched sessions only |
| `power` | `power: PowerState` | all |
| `catalog` | `catalog` | all |
| `media` | `session, items: MediaItem[]` | all |

* `approval-resolved` is derived from the `permission-resolved` chat event so unwatched sessions still clear their approvals.
* `media` reports media files a session newly mentions once they exist on disk, or that changed size or mtime (see Media). Sent for unwatched sessions too, so a gallery can update without the transcript.
* `chat` with `event.kind == "text-delta"` is dropped when the watch has `deltas: false`. The final `text` event for that block always arrives and replaces the block's deltas (same rule as the desktop: `text` removes earlier `text-delta` with the same `block`).

## Resume

* `epoch` is random per coordinator start. `seq` restarts at 0 with each epoch.
* The gateway keeps a replay buffer of the most recent hub events (bounded at 20,000 events or 16 MiB, whichever is smaller), unfiltered.
* Resume succeeds when `resume.epoch` equals the current epoch and `resume.seq` is not older than the oldest buffered event minus one. Otherwise the server sends a fresh snapshot (`resumed: false`).
* A cold launch without a saved `epoch` and `seq` sends `hello` without `resume` and takes a fresh snapshot.
* After a fresh snapshot the client keeps its cached transcripts: they are JSON files per session keyed by `entry`, so they survive restarts. For each open session it fetches `history {after: <last cached entry>}` until `hasNewer` is false.

## Requests

```
request { id, key?, command }
response { id, result, replayed }      // success
response { id, error: {code, message} } // failure
```

* `id`: connection local integer, echoed. Responses can arrive out of order (async commands).
* A command's events are sent before its response.
* `key`: client UUID (`RequestKey`). Required for every command the outbox may retry (all mutating ones). See Idempotency.

### Commands

Reused unchanged from the socket `Command` (`src/shared/coordinator.ts`):

| method | fields | result |
|---|---|---|
| `interrupt` | `session` | `{}` |
| `answer` | `session, request, choice, message?, updatedInput?` | `{}` |
| `close`, `reopen` | `session` (includes a master's workers) | `{}` |
| `archive`, `unarchive` | `session` (workers only) | `{}` |
| `rename` | `session, name` | `{}` |
| `remove` | `session` (deletes history) | `{}` |
| `model` | `session, model` | `{}` |
| `effort` | `session, effort` | `{}` |
| `configure` | `workerModels, workerEfforts` | `{}` |

`answer.choice` must be one of `approval.choices` verbatim. The phone shows those strings as buttons (labels mapped like `src/main/coordinator/view.ts` `pick`).

Phone specific:

| method | fields | result |
|---|---|---|
| `watch` | `sessions, deltas` (replaces the set) | `{}` |
| `history` | `session, before?, after?, limit?` | `HistoryPage` |
| `create` | `provider, cwd, prompt, name?, model, effort, permissionMode, accountId?, files` | `{session}` |
| `send` | `session, text, files` | `{accepted: "coordinator", entry}` |
| `upload` | `name, data` (base64) | `{path}` |
| `move` | `session, accountId` | `{}` |
| `power` | `mode: "off" \| "always"` (`PhoneKeepAwake`) | `{}` |
| `media` | `session` | `MediaList` |
| `register` | `apnsToken, environment, pushToStart, kinds` | `{}` |
| `unregister` | none | `{}` |
| `activity` | `activity, token` | `{}` |
| `activity-ended` | `activity` | `{}` |

Not available to the phone: `tool` (master orchestration only) and the desktop `create`/`move` shapes, which need config dirs the phone does not know.

* `create`: the coordinator fills `name` (default naming rules), `icon`, `accountId` (catalog active account) and `configDir` from the catalog. `cwd` must be a catalog location or an existing session's cwd; anything else is `rejected`.
* `send` and `create` pass `files` to the hub (`hub.send(session, {text, images: [], files})`; `create` makes the session with an empty prompt, then sends the prompt that way). The provider gets `Attached file: <path>` lines ahead of the text, exactly as the desktop's sends; the recorded `user` event keeps `text` without them and lists the paths in `files`, so the phone renders chips from `files`. Desktop sends also carry inline `images` on that event (dropped and counted in `omittedImages` when the event would exceed 1 MiB).
* `send` result `entry` is the history entry of the recorded `user` event, so the outbox can swap its optimistic bubble for the real one.
* `upload`: decoded size at most 10 MiB (`MAX_UPLOAD_BYTES`), else `too_large`. Saved to `~/Library/Application Support/Daycare/attachments/<uuid>/<name>`. Camera photos are downscaled on the phone to 1568 px long edge JPEG first.

### History pagination

* No cursor: the newest `limit` rows. `before: n`: rows with entry < n. `after: n`: rows with entry > n. Both: rejected as `bad_request`.
* `limit` defaults to 100, max 200 (`MAX_PAGE`). A page also stops at 1 MiB of event JSON, so it may hold fewer rows.
* Rows are oldest first. `hasOlder`/`hasNewer` say whether to keep paging. `evicted` means rows before the first retained one were discarded by the 8 MiB per session limit; show an "earlier history discarded" row.
* Entries have gaps: streamed `text-delta` rows are deleted once their `text` arrives.
* Opening a session: send `watch` including it, then `history` (no cursor). Drop live `chat` events whose `entry` is at or below the page's last entry. Scroll up with `before: <first entry>`.

## Idempotency

* Every retried command carries a `key`. The server stores `(key, device, method, result)` in the coordinator database for 7 days.
* A repeated key returns the stored result with `replayed: true` without running the command. A repeat while the first is still running waits for it.
* Same key with a different method: `bad_request`.
* Only successes and `rejected` errors are stored. `unavailable` and `internal` are not, so a retry runs again.
* Known gap: a coordinator crash between running a command and storing its key can still double run it on retry. Acceptable for single user use.

## Errors

| code | meaning | outbox action |
|---|---|---|
| `bad_request` | malformed or not allowed | drop, show error |
| `unauthorized` | wrong token | stop, ask to re-pair |
| `rejected` | hub refused (session closed, no such session, approval not pending, unknown effort) | drop, show error |
| `unavailable` | coordinator stopping, gateway starting, provider relaunch pending | retry with backoff |
| `too_large` | upload or frame over limit | drop, show error |
| `internal` | unexpected exception | retry up to 3 times |

Close codes: 4400 bad hello, 4401 unauthorized, 4408 stalled, 4409 replaced by newer connection from same device, 4413 frame too large, 4426 protocol mismatch, 4503 coordinator stopping. Any other close: reconnect with backoff (1 s doubling to 30 s, reset on `welcome`).

## Power and battery

`PowerState { mode, holding, busyCount, battery, lidClosed, error }`, `battery: { percent, pluggedIn, charging, minutesRemaining, readAt } | null`, `lidClosed: { enabled, active } | null`.

* Sent in the snapshot and as `power` events whenever any field changes. Battery is sampled every 60 s (every 20 s while discharging below 25%).
* `minutesRemaining` is time to empty when discharging and time to full when charging; null while macOS is estimating.
* `power {mode}` sets the coordinator's keep awake mode (persisted). Phone toggle "Keep awake" sends `always`, "Allow sleep" sends `off`; the schema refuses `while-running`, which is shown read only when set from the desktop.
* Keep awake (`mode`, `holding`) holds an idle system sleep assertion only (`caffeinate -i`). The display may sleep and the screen may lock; the Mac stays awake. It does not survive closing the lid.
* `lidClosed` is the desktop only "keep going with the lid closed" feature (it needs an admin password on the Mac). Phones display it, never set it. `null` when no desktop app is connected; `active` means system sleep is disabled right now, so the Mac stays up even with the lid shut.
* `error` is set when the assertion failed or stopped unexpectedly, and on Linux when a mode wants keep awake.

## Media

Images, videos and audio an agent writes or mentions (top priority: images and mp4 from agent work, not just uploads).

* `media {session}` returns `MediaList { session, items }`, newest mention first. `MediaItem { path, name, mimeType, kind, size, modifiedAt, entry }`: `path` is the real path (symlinks resolved), `kind` is `image`, `video` or `audio`, `entry` is the newest history entry mentioning it (null for a file served only because it lives under the session cwd).
* Types are sniffed from file bytes, never names: PNG, JPEG, GIF, WebP, BMP, HEIC, HEIF, AVIF, MP4/M4V, MOV, WebM, MP3, M4A, WAV, OGG, FLAC. SVG is not served.
* A file is servable for a session when its events mention it (tool inputs and output, assistant text, attached files) or its real path is inside the session's cwd. Anything else is 404, including symlinks out of the cwd.
* Bytes: `GET https://<host>:<port>/media/<session>?path=<url encoded absolute path>` (`mediaUrlPath` in `mobile.ts`) with `Authorization: Bearer <token>`. Supports `Range` (206 with `Content-Range`, 416 when unsatisfiable) so AVPlayer can stream mp4. `Content-Type` is the item's `mimeType`. Not a WebSocket frame, so the 16 MiB frame limit does not apply.
* Phones may cache by `path` plus `modifiedAt` and `size`; a `media` event with a newer `modifiedAt` replaces the cached copy.

## Push notifications

The phone sends `register` after every `welcome` (tokens can change):

* `apnsToken`: hex device token. `environment`: `development` for Xcode builds.
* `pushToStart`: Live Activity push to start token, or null.
* `kinds`: which alerts this device wants: `worker-done`, `master-done`, `approval`, `battery-low`.

Alert payload (`apns-push-type: alert`, topic = bundle id):

```json
{ "aps": { "alert": { "title": "Ada needs you", "body": "…" }, "sound": "default",
           "thread-id": "<master id>" },
  "daycare": { "kind": "approval", "session": "<id>", "request": "<request id>" } }
```

* No `category`: tapping any alert opens the app (deep link from `daycare`); there are no lock screen action buttons.

* `worker-done`/`master-done`: on `turn-end` for that role. Title `<name> finished` (or `<name> failed`), body the start of the final text (180 chars); an error turn without text says "failed".
* `approval`: on every new approval. Title `<name> needs you`, body the permission title. `apns-collapse-id` = request id.
* `battery-low`: once each at 20% and 10% while discharging (one alert when both are crossed at once); rearmed when plugged in. `apns-collapse-id` = `battery`.
* The app suppresses the banner when it is foreground on that session.
* APNs 410 or `BadDeviceToken`: the device token is deleted.

## Live Activity

* Attributes: `ActivityAttributes {host}`. Content state: `ActivityState {running, runningCount, approvals, batteryPercent, charging, keepAwake, updatedAt}`. Times are epoch seconds as numbers; Swift decodes them as `Double`, not `Date`.
* The app starts the activity when work is running and it is foreground, or the coordinator starts it with the push to start token. The app reports each activity's update token with `activity`, and `activity-ended` when it ends.
* Coordinator sends `apns-push-type: liveactivity`, topic `<bundle id>.push-type.liveactivity`, `event: update` on change, coalesced to at most one per 15 s at priority 5; approval changes go out at priority 10. It sends `event: end` with a `dismissal-date` after 10 minutes with nothing running or waiting, then forgets those activity tokens.
* When work starts and a device has no activity token but a `pushToStart` token, the coordinator sends `event: start` with `attributes-type: "DaycareActivityAttributes"`, `attributes: {host}` and an alert.
* `aps.timestamp` is epoch seconds; `content-state` is `ActivityState`.
